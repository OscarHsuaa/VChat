## 2. TCP 帧、消息序列化与分发

**帧边界。** UTF-8 文本，每帧以 `\n` 结束。服务器给每个 `QTcpSocket*` 保存独立 `QByteArray` 缓冲，`readyRead` 追加 `readAll()`，按换行拆出完整帧后分支处理。`sendLine()` 负责 UTF-8 写出。聊天主窗口由 `on_socketReadyRead()` 对 `receiveBuffer` 做同样拆帧，再调用 `appendIncomingLine()`。结构化帧通常采用 `QJsonDocument::Compact` 的 UTF-8 JSON 加 Base64；登录、加入与部分兼容帧使用分隔符文本。

## 3. 登录、成员与房主的可信来源

1. **登录身份**：`authenticateUser()` 使用参数化 SQL 按用户名查询 `users`。若有非空 `password_hash` 则核验哈希，否则走旧密码兼容分支。登录获得数据库 `users.id` 和昵称。服务端生成 UUID 令牌并保存在进程内 `loginSessions`，用 UTC 记录签发时间。`JOIN` 以令牌与昵称/现有会话校验，接受后把 `qint64` 账号绑定到 `onlineUserIds[socket]`。按实现 `JOIN` 检查 86400 秒窗口并刷新时间，进程重启后原令牌不再有效。
2. **房间身份**：登录后以服务端 `activeRooms[socket]` 作为当前房间。`CHAT2` 取该值，`ROOM switch/history` 对请求中的房间 ID 查成员关系。`RoomStore::isMember()` 查询 `room_members` 并关联 `rooms.dissolved_at IS NULL`。一般房间由 `RoomStore::create()` 生成 UUID；`class-room` 是固定常量。客户端 `currentRoomId` 只负责界面和过滤，授权以服务端查询为准。
3. **房主身份**：`RoomStore::create()` 在同一事务写入 `rooms.owner_id` 和对应的 `room_members.role='owner'`。`canManage()` 以两者匹配判断房主，普通成员也可能因 `allow_member_*` 获得部分房间管理权限。任务授权可沿用账户和成员查询、房主判定条件，不能直接将 `canManage()` 的返回值解释成任务批准资格。

证据：[authenticateUser](../ChatServer/main.cpp#L489) · [登录与会话绑定](../ChatServer/main.cpp#L753) · [ROOM 的 actor 来源](../ChatServer/main.cpp#L877) · [RoomStore 成员校验](../ChatServer/roomstore.cpp#L74) · [房主判断](../ChatServer/roomstore.cpp#L127) · [房间创建](../ChatServer/roomstore.cpp#L325)。

### 大厅的授权建议（待产品确认）

本机 `vchat_demo.rooms` 确认 `class-room` 为 `public`、`owner_id IS NULL`、`dissolved_at IS NULL`；成员计数为 41 条 `member`，无 `owner`。`003_rooms.sql` 将其作为系统房间插入，`ensureLobbyMember()` 以 `member` 加入，`canManage()` 明确拒绝大厅房间管理操作。

| 房间及角色 | 按方案允许批准的条件 |
| --- | --- |
| 大厅任务发起人 | 已认证、仍属大厅，服务端任务记录的 `creator_id` 等于 actor，提交的计划版本和摘要匹配当前计划。 |
| 大厅其他成员 | 拒绝批准。同属大厅、昵称或客户端自报的房主标识均不构成授权。 |
| 有房主的普通房间 | 发起人可批准。代批须是当前未解散房间的成员，且 `rooms.owner_id` 非空并等于 actor，同时成员角色为 `owner`。 |
| 退出、被移除、房间解散、旧计划 | 批准和执行前重新检查；不再符合条件时停止启动，按待确认策略记录失效或要求重批。 |

批准时从任务记录读取 `room_id/creator_id`，用登录会话取 actor，条件更新须绑定当前 `plan_version/plan_hash`。执行阶段以持久化授权的批准人重新核对，无需依赖同一个 socket 仍在线。普通房间的房主代批与大厅发起人批准应分开验收。拒绝、取消、改计划和报告发布是独立权限，见 [待确认项](V0.5_风险与待确认事项.md#1-进入实现前要确认的决定)。证据：[大厅种子](../ChatServer/migrations/003_rooms.sql#L39) · [大厅入会](../ChatServer/roomstore.cpp#L64) · [管理权限分支](../ChatServer/roomstore.cpp#L127)。

## 4. DeepSeek Flash、上下文与流式输出

1. **触发**：`MainWindow` 从选中的提及对象生成 `mentions`。服务端验证位置、名称和对象身份，结构化 Vivi 需匹配 `type=ai`、`id=vivi`、`name=Vivi`，另有文本 `@Vivi` 正则回退。已验证的同名真人提及优先，避免误触发。普通消息写库后仍进入 `AiRoom::addUserMessage()` 用于更新上下文；只有 `askVivi` 成立时生成请求。见 [客户端发送](../ChatDemo_1/mainwindow.cpp#L1933) 和 [服务端提及及触发](../ChatServer/main.cpp#L1437)。
2. **上下文**：`roomFor(roomId)` 按房间建立 `AiRoom`，其 `HistoryLoader` 通过工作线程读取该房间、截至当前消息 `sequence_id` 的团队记录。`readAiHistory()` 查询普通文本及合格 AI 历史；`AiRoom::addUserMessage()` 按序号合并内存快照和数据库结果，按消息 ID 去重并排除当前问题及发问时未完成的 AI 回复。`makeContext()` 添加系统指令，限制消息条数（默认 20，配置范围 1～50）、单条及总字符预算，最后单独追加本次问题。见 [查询](../ChatServer/main.cpp#L72) · [异步加载](../ChatServer/main.cpp#L619) · [合并和预算](../ChatServer/airoom.cpp#L54)。
3. **模型调用**：`AiService::complete()` 和 `stream()` 通过 `QNetworkAccessManager::post()` 发 JSON 到 `/chat/completions`，配置值为 `deepseek-flash`、`thinking.disabled`、`max_tokens=1024`，各自设置 `stream=false/true`。默认 HTTP 传输超时 30 秒。API 密钥读服务端环境，Windows 有用户环境回读；`isConfigured()` 检查密钥存在与 Qt TLS 支持。HTTP 错误分类、超时、输出格式错误回调上层，现有两条方法均未提供任务计划 JSON Schema 校验。此次以源码确认调用方式，未探测远端实际账户能力。见 [服务初始化](../ChatServer/main.cpp#L559) · [AiService](../ChatServer/aiservice.cpp#L98) · [默认超时](../ChatServer/aiservice.h#L15)。
4. **流的转换**：`SseParser` 按空行解析 `data:` 事件、追加 `choices[0].delta.content`，以 `[DONE]` 为完成标记。`AiRoom::startNext()` 维护每房间最多 3 个活动回复、默认 12 个额外排队/等待席位和活动请求 90 秒超时。流事件持有 `request_id/message_id/generation_id/sequence` 和回复关联，`broadcastAi()` 持久化起止状态并向当前活动房间转发，增量不逐片写库。客户端 `appendAiStreamEvent()` 匹配请求与生成标识、过滤序列，在 GUI 定时器逐步渲染并以 `AiMarkdownWidget` 完成最终显示。见 [SSE](../ChatServer/aiservice.cpp#L17) · [队列与回调](../ChatServer/airoom.cpp#L283) · [客户端组装](../ChatDemo_1/mainwindow.cpp#L3393)。
5. **现有任务形态参考**：`AI_SUMMARY` 也调用 `AiService::stream()`，但总结上下文只取当前房间最近最多 30 条用户讨论；进度仅回请求 socket。`summaryJobs` 与未分享的 `completedSummaries` 保存在进程内。分享另走写库及广播。这个模式适合参考请求关联和结果呈现，既有 `AiRoom` 队列和总结状态都不等同于可恢复的 Agent 任务。见 [总结分支](../ChatServer/main.cpp#L1282) 和 [分享分支](../ChatServer/main.cpp#L1166)。

## 5. MySQL 实际结构与事务

本机 `SELECT VERSION()` 为 **MySQL Community Server 8.4.8**。`@@session.time_zone`、`@@global.time_zone` 均为 `SYSTEM`，`NOW()` 与 `UTC_TIMESTAMP()` 相差 **+480 分钟**。`vchat_demo` 默认 `utf8mb4_general_ci`；实查八张表均为 InnoDB、Dynamic 行格式。房间和聊天历史表使用 `utf8mb4_unicode_ci`，旧业务表按下表归类。当前实例的查询结果中未发现 `vchat_agent`。

| 表 | 实查关键类型、索引和职责 |
| --- | --- |
| `users` | `id INT` 有符号、主键、自增；`username VARCHAR(50)` 唯一；`nickname VARCHAR(50)`；`password_hash VARCHAR(128) NULL`；`created_at DATETIME` 可空。`authenticateUser()` 将 ID 读为 `qint64`。 |
| `rooms` | `room_id VARCHAR(64)` 主键；`owner_id BIGINT NULL`；`room_type ENUM('invite_only','public')`；权限字段和 `join_policy` 已存在；`created_at`、`updated_at`、`dissolved_at` 为 `DATETIME(3)`，解散时间可空。 |
| `room_members` | 主键 `(room_id,user_id)`；`room_id VARCHAR(64)` 外键至 `rooms`，`user_id BIGINT`，`role ENUM('owner','member')`，`joined_at DATETIME(3)`。另有 `(user_id,room_id)` 索引。 |
| `room_invites` | `token_hash` 主键，`room_id VARCHAR(64)` 外键至 `rooms`；`created_by BIGINT` / `used_by BIGINT NULL`；创建、过期和使用时间为 `DATETIME(3)`。 |
| `room_direct_invites` | `invite_id CHAR(36)` 主键，`(room_id,recipient_user_id)` 唯一，`room_id VARCHAR(64)` 外键至 `rooms`；邀请双方 ID 为 `BIGINT`；创建、过期和回应时间为 `DATETIME(3)`。 |
| `chat_history` | `sequence_id BIGINT UNSIGNED` 主键、自增；`message_id CHAR(36)` 唯一，`room_id VARCHAR(64)`；`sender_id/recipient_user_id BIGINT NULL`，`original_request_id BIGINT UNSIGNED NULL`；`created_at DATETIME(3)`。有房间顺序、可见性、回复关联索引，`legacy_message_id` 和 `share_request_id` 各有唯一约束。实际枚举涵盖 `user`、`ai`、`discussion_summary`。 |
| `messages` | 旧消息表 `id INT` 自增主键，`sent_at DATETIME` 可空。`openDatabase()` 在启动时读取并按 `legacy_message_id` 幂等导入。 |
| `online_users` | 实查表存在，`id INT` 自增主键，`username` 有唯一索引。当前在线身份以 `main.cpp` 进程中的 `onlineUsers/onlineUserIds/activeRooms` 为依据。 |

现有外键只发现房间成员及两类邀请的 `room_id` 指向 `rooms.room_id`，未发现这些表对 `users.id` 的外键。迁移脚本明确允许旧安装使用不同用户 ID 类型。Agent 的 `room_id` 可对齐现有字符串键，账号外部引用应按本机 `INT` 与应用 `qint64`/业务表 `BIGINT` 的差异明确兼容策略，不能将草案的 `VARCHAR(64)` 账号字段当成现状。

**时间。** `saveUserHistory()` 将服务端接收时间写为本地 `DATETIME(3)`，实时 `CHAT2` 使用同一时刻的 UTC ISO 8601。`storedMessageTime()` 为无时区本地记录附上服务端系统时区再输出 UTC，客户端 `ChatTime::parse()` 转当地时间。房间详情、邀请和总结生成时间仍有不显式附带时区的路径。因此新 Agent 应单独约定显式 UTC 存储/序列化，并独立处理旧表的时间语义。见 [storedMessageTime](../ChatServer/main.cpp#L62) · [房间时间格式](../ChatServer/roomstore.cpp#L91) · [客户端时间解析](../ChatDemo_1/chattimeutils.h#L10)。

**连接和事务。** `openDatabase()` 在服务端主线程建立默认 QMYSQL 连接，默认业务库 `vchat_demo`，测试可用 `VCHAT_TEST_DB`。普通登录、房间操作和历史写入使用参数化 `QSqlQuery`。`registerUser()`、`RoomStore::create()`、`updatePermissions()`、`redeem()`、`sendDirectInvites()` 等在各自函数内直接 `transaction/commit/rollback`，多处用 `FOR UPDATE` 或带条件更新保护身份和并发状态。没有发现通用事务封装。`readAiHistory()` 在工作线程建立独立命名连接，结果返回后关闭、释放并移除连接。可复用连接归属和事务写法，Agent 多表操作需要自己的事务边界。见 [openDatabase](../ChatServer/main.cpp#L153) · [注册事务](../ChatServer/main.cpp#L443) · [房间事务](../ChatServer/roomstore.cpp#L325) · [查询连接](../ChatServer/main.cpp#L72)。

**数据库证据的复核方法。** 本次由现有 MySQL 客户端执行 `SELECT VERSION()`，读取 `information_schema.SCHEMATA/TABLES/COLUMNS/STATISTICS/KEY_COLUMN_USAGE`，查询 `rooms WHERE room_id='class-room'` 及 `room_members` 按角色聚合，上述均为 `SELECT`。异地部署的版本、账号字段和运行时权限待确认。

## 6. 线程与生命周期

- **ChatServer 主线程**：`QCoreApplication` 启动，检查/打开数据库，然后以 `QHostAddress::Any` 监听默认 8080 端口，非默认测试端口走 `LocalHost`。`QTcpServer/QTcpSocket` 回调、默认数据库连接、`AiService` 网络对象、`AiRoom` 计时器和广播都由主事件循环驱动。普通业务 SQL 在这些回调中同步执行；大查询或文件读取如果沿用该路径会阻塞其他连接。见 [启动](../ChatServer/main.cpp#L524) · [监听](../ChatServer/main.cpp#L1600)。
- **工作线程**：两处 `QtConcurrent::run()` 用于普通 Vivi 和总结的历史读取；任务捕获库名、房间和查询边界等值，独立 QMYSQL 连接。`QFutureWatcher::finished` 在主线程使用结果，普通 Vivi 绑定 `AiRoom`，总结使用 `QPointer<QTcpSocket>` 再核对请求 ID、账号、房间。见 [Vivi 查询回调](../ChatServer/main.cpp#L625) · [总结查询回调](../ChatServer/main.cpp#L1313)。
- **退出与恢复**：连接断开时移除 socket 的缓冲、在线账号、活动房间，取消该 socket 的总结并释放 socket。共享 Vivi 有独立于单一连接的房间状态，房间解散时 `cancelAll()`。进程持有会话及 AI 队列。成功绑定端口后启动代码会把 `chat_history` 中未完成的 `pending` AI 行标为失败，现有对话回复不会从中断处续跑；旧历史仍按数据库回放。见 [房间解散](../ChatServer/main.cpp#L1098) · [断连](../ChatServer/main.cpp#L1565) · [中断恢复](../ChatServer/main.cpp#L1610)。
- **Qt 客户端**：`QApplication` 管理窗口与 GUI 事件循环。`MainWindow` 拥有 `QTcpSocket`，异步槽在 GUI 线程处理网络和 QWidget，`QTimer` 同线程节流/驱动 AI 文本绘制。`LoginDialog` 登录、注册走临时 socket 的 `waitFor*`，为 UI 线程上的同步等待。Agent 进度可沿现有异步消息格局进入 GUI；后续预览和下载应另确认大小限制与异步处理。见 [入口](../ChatDemo_1/main.cpp#L7) · [登录等待](../ChatDemo_1/logindialog.cpp#L1056) · [聊天信号](../ChatDemo_1/mainwindow.cpp#L1798) · [流式绘制](../ChatDemo_1/mainwindow.cpp#L3312)。

TASK-000 结论：现有聊天服务已具备可复用的身份、成员、收发、模型和界面模块。计划校验、任务授权、持久化状态机、文件执行与审计是后续任务所需的新业务能力。交付边界为本报告及三份配套文档。
